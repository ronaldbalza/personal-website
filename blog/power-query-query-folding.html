    Query Folding in Power Query: Why Your Refresh Is Slow

    When a Power BI refresh crawls, the cause is often a single Power Query step that stopped the work being pushed back to the database. Here's how to find it and what to do about it.

    Ronald Balza
    BI Reporting Analyst
    Mar 26, 2024•6 min read

    Power Query looks like it transforms data step by step on your machine. Against a database, that's not what should happen. For sources that support it, the Power Query engine translates your applied steps into a single native query (SQL, for a relational database) and lets the source do the work. That translation is called query folding.

    When folding works, filtering a 50-million-row table to last year's data sends a WHERE clause to the server and only the matching rows travel over the network. When it breaks, Power Query may pull the whole table and filter it locally. Same result, very different refresh time.

    How to check whether a step folds

    • View Native Query. In Power Query Editor, right-click a step in Applied Steps. If View Native Query is enabled, the query up to that step folds, and you can see the SQL. If it's greyed out, it may not fold (some connectors fold without exposing the query, so treat this as a strong hint rather than proof).
    • Step folding indicators. Power Query Online (dataflows) shows an icon next to each step indicating whether it folds, doesn't fold or might fold.
    • Query diagnostics (Tools → Start Diagnostics) record what was actually sent to the source during a refresh, which is the definitive answer.

    What usually folds, and what usually breaks it

    Usually folds (relational sources)Often breaks folding
    Choosing or removing columnsAdding an index column
    Filtering rowsTable.Buffer and other buffering functions
    SortingMerging queries from different sources
    Group by and basic aggregationsCustom M functions invoked per row
    Joins to tables in the same databaseMany text and date transformations without a SQL equivalent
    Changing data types (most cases)Pivoting/unpivoting on some connectors

    The exact list depends on the connector. Folding is decided per step, and once a step breaks folding, every step after it runs locally, even ones that would normally fold.

    Fix #1: put foldable steps first

    Because folding stops at the first non-foldable step, step order matters. Do column selection and row filtering at the top of the query, and push anything that breaks folding to the end, where it operates on a small result set: 

    let
    Source   = Sql.Database("sql-prod-01", "SalesDW"),
    Orders   = Source{[Schema = "dbo", Item = "FactOrders"]}[Data],
    // These fold into one SELECT … WHERE …
    Columns  = Table.SelectColumns(Orders,
                 {"OrderID", "OrderDate", "CustomerKey", "SalesAmount"}),
    Filtered = Table.SelectRows(Columns, each [OrderDate] >= #date(2022, 1, 1)),
    // Non-foldable step last, on the already-reduced data
    Indexed  = Table.AddIndexColumn(Filtered, "RowNo", 1, 1, Int64.Type)
in
    Indexed

    Better still, ask whether the non-foldable step is needed at all. An index column is often only used to create a key that the source table already has.

    Fix #2: push logic into a view

    If a transformation can't fold and runs on lots of data, the most robust fix is to do it in the source: a SQL view (or a table in the warehouse) that Power Query reads with a simple, fully foldable query. It's also easier to test and reuse across reports than logic hidden inside one PBIX file.

    Fix #3: native queries that still fold

    Pasting SQL into the connector dialog's "SQL statement" box works, but steps you add afterwards won't fold on top of it. For SQL Server, Value.NativeQuery with the EnableFolding option lets later steps fold on top of your SQL: 

    let
    Source = Sql.Database("sql-prod-01", "SalesDW"),
    Orders = Value.NativeQuery(
                 Source,
                 "SELECT OrderID, OrderDate, CustomerKey, SalesAmount
                  FROM dbo.FactOrders
                  WHERE IsCancelled = 0",
                 null,
                 [EnableFolding = true]
             ),
    // This filter is folded into the query above
    Recent = Table.SelectRows(Orders, each [OrderDate] >= #date(2023, 1, 1))
in
    Recent

    Why folding matters for incremental refresh

    Incremental refresh splits a table into date partitions and filters each one using the RangeStart and RangeEnd parameters (both must be of type Date/Time). The filter should use >= on one boundary and < on the other so rows aren't counted in two partitions: 

    Filtered = Table.SelectRows(Orders, each
               [OrderDateTime] >= RangeStart and [OrderDateTime] < RangeEnd)
    ⚠️

    If this filter doesn't fold, incremental refresh loses its benefit. Each partition refresh would pull the full table and filter locally. Power BI Desktop warns when it can't confirm the query folds; take that warning seriously and fix the step order before publishing.

    Wrapping up

    When a refresh is slow, check folding before anything else: right-click down the Applied Steps, find the first step where View Native Query goes grey, and ask whether that step can move, be removed or be pushed into the source. It's usually the quickest performance win in a Power BI model.
