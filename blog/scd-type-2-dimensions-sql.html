    Slowly Changing Dimensions Type 2 in SQL: A Practical Load Pattern

    When a customer moves region, should last year's sales move with them? If the answer is no, you need a Type 2 dimension. Here's a load pattern in T-SQL that's simple to reason about and safe to re-run.

    Ronald Balza
    BI Reporting Analyst
    Aug 19, 2025•8 min read

    Dimensions change. A customer moves to a different sales region, a product is reassigned to a new category, an employee changes cost centre. How the warehouse handles those changes decides whether historical reports stay stable or quietly rewrite themselves.

    TypeBehaviourEffect on history
    Type 1Overwrite the attributePast facts are reported under the new value
    Type 2Insert a new row version, expire the old onePast facts keep the value that was true at the time

    Most dimensions mix both: a typo fix in a customer name should be Type 1, while a region change usually needs Type 2 so last year's regional totals don't move. This article covers a Type 2 load in T-SQL.

    The dimension table

    CREATE TABLE dim.Customer (
    CustomerKey   INT IDENTITY(1,1) NOT NULL,   -- surrogate key, one per version
    CustomerID    VARCHAR(20)   NOT NULL,       -- business key from the source
    CustomerName  NVARCHAR(200) NOT NULL,
    Segment       NVARCHAR(50)  NULL,
    Region        NVARCHAR(50)  NULL,
    RowHash       VARBINARY(32) NOT NULL,       -- hash of the Type 2 attributes
    ValidFrom     DATE          NOT NULL,
    ValidTo       DATE          NOT NULL,       -- '9999-12-31' for the current row
    IsCurrent     BIT           NOT NULL,
    CONSTRAINT PK_dim_Customer PRIMARY KEY (CustomerKey)
);

    Three design points:

    • Surrogate key per version. Facts store CustomerKey, which pins each fact to the version that was current when it happened.
    • A far-future ValidTo instead of NULL keeps range lookups simple (BETWEEN-style logic without ISNULL).
    • A row hash makes change detection a single comparison instead of comparing every column, with all the NULL-handling that implies.

    Step 1 — Stage and hash the incoming data

    Land the latest source extract in a staging table and compute a hash over the Type 2 attributes (here Segment and Region; CustomerName is handled as Type 1 below). Use a delimiter so that ('AB', 'C') and ('A', 'BC') don't produce the same input: 

    UPDATE stg.Customer
SET    RowHash = HASHBYTES('SHA2_256',
           CONCAT(Segment, '|', Region));   -- Type 2 attributes only

    CONCAT treats NULL as an empty string, so a value changing from NULL to empty won't register as a change. If that distinction matters, wrap columns in COALESCE(col, '<null>') first.

    Step 2 — Expire changed rows, then insert new versions

    The load is two statements. First, close off current rows whose hash has changed. Then insert a row for every staged customer that has no current row: that covers brand-new customers and the customers whose rows were just expired. 

    CREATE OR ALTER PROCEDURE etl.Load_DimCustomer
    @LoadDate DATE
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- 1. Expire current rows whose tracked attributes changed
        UPDATE d
        SET    d.ValidTo   = DATEADD(DAY, -1, @LoadDate),
               d.IsCurrent = 0
        FROM   dim.Customer AS d
        JOIN   stg.Customer AS s
               ON s.CustomerID = d.CustomerID
        WHERE  d.IsCurrent = 1
          AND  d.RowHash <> s.RowHash;

        -- 2. Insert new customers and new versions of changed ones
        INSERT INTO dim.Customer
              (CustomerID, CustomerName, Segment, Region, RowHash,
               ValidFrom, ValidTo, IsCurrent)
        SELECT s.CustomerID, s.CustomerName, s.Segment, s.Region, s.RowHash,
               @LoadDate, '9999-12-31', 1
        FROM   stg.Customer AS s
        LEFT JOIN dim.Customer AS d
               ON d.CustomerID = s.CustomerID
              AND d.IsCurrent  = 1
        WHERE  d.CustomerID IS NULL;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;   -- re-raise so the orchestrator marks the run as failed
    END CATCH
END;

    Why this shape works well:

    • It's re-runnable. Run it twice with the same staging data and the second run changes nothing: hashes match, and every customer already has a current row.
    • It's atomic. Both statements commit together or not at all, so the dimension is never left with a customer that has no current row.
    • No overlapping ranges. The expired row ends the day before the new one starts, so a date falls into exactly one version.
    ⚠️

    Platform note. This is SQL Server / Azure SQL syntax. Dedicated SQL pools in Azure Synapse don't support ANSI joins in the FROM clause of an UPDATE, and identity values there aren't guaranteed to be sequential. Rewrite step 1 with a subquery (or a CTAS swap) on Synapse, and on Snowflake express the same logic with MERGE or UPDATE … FROM.

    Handling Type 1 attributes in the same dimension

    Attributes that should be overwritten rather than versioned, like a corrected CustomerName, are kept out of RowHash and updated across all versions of the customer in a separate statement: 

    UPDATE d
SET    d.CustomerName = s.CustomerName
FROM   dim.Customer AS d
JOIN   stg.Customer AS s ON s.CustomerID = d.CustomerID
WHERE  d.CustomerName <> s.CustomerName;

    Decide per attribute with the business which behaviour they expect, and write it down. "Why did last year's numbers change?" is much easier to answer when the rules are documented.

    Step 3 — Look up the right version when loading facts

    Each fact row should get the surrogate key of the version that was valid on the transaction date: 

    INSERT INTO fact.Sales (DateKey, CustomerKey, ProductKey, SalesAmount)
SELECT CONVERT(INT, CONVERT(CHAR(8), s.OrderDate, 112)),   -- yyyymmdd
       COALESCE(c.CustomerKey, -1),          -- -1 = "Unknown" member
       p.ProductKey,
       s.SalesAmount
FROM   stg.Sales AS s
LEFT JOIN dim.Customer AS c
       ON  c.CustomerID = s.CustomerID
       AND s.OrderDate BETWEEN c.ValidFrom AND c.ValidTo
JOIN   dim.Product AS p
       ON  p.ProductID = s.ProductID AND p.IsCurrent = 1;

    The -1 "Unknown" member (a row you insert into the dimension once, with that key) keeps facts from being dropped when a customer hasn't arrived in the dimension yet, and makes those rows easy to find and fix.

    What it means in Power BI

    Relate the fact to the dimension on CustomerKey and history behaves correctly: sales made while a customer was in APAC stay in APAC. When users want to see all history under the current attributes ("where are this customer's sales now?"), add the current values as extra columns on every version (e.g. CurrentRegion), or relate on the business key to a current-only view of the dimension. Give both options clear names, and the report can answer either question.

    Wrapping up

    A Type 2 load doesn't need to be complicated: hash the tracked attributes, expire what changed, insert what's missing, all in one transaction. Pair it with a date-range lookup when loading facts and an "Unknown" member, and historical reports stay exactly as they were when they were first published.
