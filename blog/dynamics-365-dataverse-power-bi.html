    Getting Dynamics 365 Data into Power BI: Dataverse Connector, Fabric Link and the Web API

    Dynamics 365 stores its data in Dataverse, and there are several ways to get it out. They differ a lot in freshness, volume limits and how much modelling they leave you to do. Here's how I choose between them.

    Ronald Balza
    BI Reporting Analyst
    Jul 22, 2026•8 min read

    Dynamics 365 Sales, Customer Service and the other model-driven apps keep their data in Microsoft Dataverse. Every Dynamics "entity" (account, contact, opportunity, case) is a Dataverse table with a logical name like opportunity and columns like estimatedvalue. Reporting on Dynamics means getting Dataverse tables into a model, and the route you pick shapes everything after it.

    The four main options

    OptionHow it worksGood for
    Dataverse connectorPower BI queries Dataverse through its read-only SQL (TDS) endpoint, in Import or DirectQuerySmall to medium tables, quick reports, near-live DirectQuery
    Link to Microsoft FabricDataverse maintains Delta copies of selected tables in Dataverse-managed storage, exposed to a Fabric workspace through shortcutsLarge volumes, joining with other data, Direct Lake
    Azure Synapse Link for DataverseContinuously exports tables to your own ADLS Gen2 account (optionally as Delta)Existing Azure data platforms that want the files
    Web API (OData)REST queries against /api/data/v9.2/Custom extraction in a pipeline, specific filtered pulls

    The Dataverse connector (TDS endpoint)

    In Power BI Desktop, Get data → Dataverse lists your environments and their tables. Under the hood it uses the Dataverse TDS endpoint, which accepts a subset of T-SQL. The endpoint has to be enabled for the environment (Power Platform admin center → environment Settings → Product → Features), and it respects Dataverse security: users only see the rows their security roles allow.

    Because it speaks SQL, you can also connect from SQL Server Management Studio or Azure Data Studio using the environment host (e.g. yourorg.crm.dynamics.com) and Microsoft Entra authentication, which is handy for exploring data before modelling it: 

    SELECT TOP 100
       o.opportunityid,
       o.name,
       o.statecode,
       o.statecodename,          -- label for the choice value
       o.estimatedvalue,
       o.estimatedvalue_base,    -- converted to the org's base currency
       o.parentaccountid,
       o.parentaccountidname,    -- display name of the lookup target
       o.owneridname,
       o.estimatedclosedate,
       o.modifiedon
FROM   opportunity AS o
WHERE  o.statecode = 0;          -- open opportunities

    Notice the …name columns: the SQL endpoint exposes a label column next to each choice (option set) and lookup column, which saves you building lookup tables for status reasons and owners.

    ⚠️

    Know the limits. The TDS endpoint is designed for reporting queries, not bulk extraction. Queries are subject to documented result-size and timeout limits, so importing very large tables (activity history, audit-style tables) through the connector can fail or be slow. That's the point to move to Link to Fabric or Synapse Link.

    Link to Microsoft Fabric

    For larger models, Link to Microsoft Fabric (set up from the Power Apps maker portal under Analyze → Link to Microsoft Fabric) has Dataverse keep Delta tables of your selected tables in sync, and creates a Fabric lakehouse with shortcuts to them. From there you can:

    • Query them through the lakehouse's SQL analytics endpoint.
    • Join them with data from other systems in notebooks or a warehouse (for example, Salesforce data for a combined pipeline report).
    • Build gold tables and a Direct Lake semantic model on top, with no import refresh against Dataverse.

    It requires a Fabric capacity in the same region as the Dataverse environment, and the data still counts toward Dataverse storage. Check both before proposing it.

    The Web API, when you need control

    For pipeline-driven extraction (for example, an ETL tool loading Snowflake), the Dataverse Web API is the standard interface. Request formatted values with the Prefer header to get labels alongside codes: 

    GET https://yourorg.crm.dynamics.com/api/data/v9.2/opportunities
    ?$select=name,estimatedvalue,statecode,_parentaccountid_value,modifiedon
    &$filter=modifiedon gt 2026-07-01T00:00:00Z
Authorization: Bearer {token}
Accept: application/json
Prefer: odata.include-annotations="OData.Community.Display.V1.FormattedValue",odata.maxpagesize=5000

    Lookups appear as _<name>_value properties holding the related record's GUID. Results are paged: keep following @odata.nextLink until it's absent. Use an app registration (application user) with a security role that grants read access, rather than a named user's credentials.

    Modelling gotchas that apply whichever route you use

    • Logical names vs display names. The UI says "Est. Revenue"; the column is estimatedvalue. Rename in the model or a view so report authors see business-friendly names.
    • Status vs status reason. statecode is the system state (for opportunity: 0 Open, 1 Won, 2 Lost) and is fixed; statuscode is the customisable status reason within each state. Base KPIs on statecode, and use statuscode for detail.
    • Dates are stored in UTC. Date/time columns with User Local behaviour are stored in UTC and converted in the app for each user. A deal closed at 9 am in Sydney is stored on the previous day in UTC, so convert to the business time zone before deriving a date key, or month-end totals will drift.
    • Polymorphic lookups. customerid on an opportunity can point to an account or a contact. Use parentaccountid when you need the account, or resolve the type explicitly.
    • Inactive records. Most tables have active/inactive states. Decide per report whether inactive accounts and contacts belong in the dimension (usually yes, so historical facts still find their customer).

    How I'd choose

    1. A report on a handful of modest tables → Dataverse connector, Import mode, scheduled refresh.
    2. A report that must reflect changes within minutes → Dataverse connector in DirectQuery, kept small and simple.
    3. Large tables, or Dynamics joined with other systems → Link to Fabric (or Synapse Link, if the platform is Azure-based), then a proper gold layer.
    4. A central warehouse elsewhere, such as Snowflake → Web API extraction via your ETL tool, incremental on modifiedon.

    Wrapping up

    There's no single "right" way to get Dynamics data into Power BI. There's a right way for the data volume, freshness and platform you have. Whichever you pick, deal with labels, status codes and UTC dates once, in a view or gold table, so every report built on Dynamics data gets them right automatically.
