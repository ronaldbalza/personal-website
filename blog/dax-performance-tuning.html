    Tuning Slow DAX: A Practical Workflow with Performance Analyzer and DAX Studio

    "The report is slow" can mean a slow measure, a bloated model, too many visuals or a source query. This is the workflow I use to find out which, and the DAX changes that usually fix it.

    Ronald Balza
    BI Reporting Analyst
    Jan 14, 2025•9 min read

    Performance tuning in Power BI goes wrong when it starts with guesses: rewriting a measure that wasn't the problem, or blaming the data source for a slow visual that's actually a model design issue. A few free tools make it possible to measure instead of guess.

    Step 1 — Find the slow visual

    In Power BI Desktop, open Performance Analyzer (Optimize ribbon), click Start recording, then Refresh visuals. Each visual reports three timings:

    • DAX query: time for the semantic model to answer the visual's query.
    • Visual display: time to render, which grows with the number of data points and with some custom visuals.
    • Other: mostly waiting, for example behind other visuals on the page.

    If DAX query dominates, the problem is in the model or measures. Use Copy query on that visual to take the exact query into DAX Studio. If visual display dominates, reduce the data points or swap the visual.

    Step 2 — Read the server timings

    DAX Studio connects to the model open in Desktop. Paste the query, turn on Server Timings and run it (clear the cache first, so you measure a cold run). The key split is between the two engines:

    EngineWhat it doesCharacteristics
    Storage engine (SE)Scans compressed columns, applies filters, does simple aggregationsFast and multi-threaded; results can be cached
    Formula engine (FE)Everything else: complex expressions, iterating rows, combining SE resultsSingle-threaded; no cache

    A healthy query spends most of its time in the storage engine with a small number of queries. Warning signs:

    • High FE time: logic the storage engine couldn't do, often row-by-row iteration with complex expressions.
    • Many SE queries (hundreds or thousands): the formula engine is calling the storage engine once per row or per cell.
    • CallbackDataID in the SE query text: the storage engine had to call back into the formula engine for each row, which is slow and prevents caching.
    • Large materialisations: an SE query returning far more rows than the visual shows.

    Step 3 — Check the model size

    Slow measures are sometimes just big columns. DAX Studio's View Metrics (VertiPaq Analyzer) lists every table and column with its size and cardinality. The usual suspects:

    • High-cardinality columns nobody uses: transaction GUIDs, free-text comments, timestamps to the second.
    • Datetime columns where a date is enough: splitting date and time into two columns reduces cardinality dramatically.
    • Auto date/time tables: Power BI creates a hidden date table for every date column when this option is on. With a proper date table, turn it off (Options → Data Load).

    Removing an unused column is the cheapest performance win there is: less memory, faster refresh and faster scans.

    Step 4 — The rewrites that help most

    Filter columns, not tables

    Passing a whole table to FILTER inside CALCULATE forces the engine to work with every column of that table. Filtering just the column you need lets the storage engine apply it directly: 

    -- Slower: iterates the whole Sales table
Large Orders Sales =
CALCULATE ( [Sales Amount], FILTER ( Sales, Sales[NetAmount] > 1000 ) )

-- Faster: a simple column predicate
Large Orders Sales =
CALCULATE ( [Sales Amount], Sales[NetAmount] > 1000 )

    Note the two aren't always identical in meaning: the boolean form replaces any existing filter on Sales[NetAmount]. Wrap it in KEEPFILTERS if it should intersect with filters from the report instead.

    Store intermediate results in variables

    Variables are evaluated once, where they're defined. Referencing a measure several times in an expression may evaluate it several times; a variable avoids that and makes the code easier to read: 

    Margin % =
VAR _sales = [Sales Amount]
VAR _cost  = [Cost Amount]
RETURN
    IF ( _sales <> 0, ( _sales - _cost ) / _sales )

    Keep iterators simple

    SUMX over a fact table is fine when the expression per row is simple arithmetic, which the storage engine can handle. Conditional logic per row (IF, SWITCH) is what tends to produce CallbackDataID. Often the condition can move into a filter instead: 

    -- Per-row IF inside the iterator
Online Sales =
SUMX ( Sales, IF ( Sales[Channel] = "Online", Sales[Qty] * Sales[UnitPrice] ) )

-- Condition as a filter; the iterator stays simple
-- (KEEPFILTERS keeps the original behaviour when a channel slicer is applied)
Online Sales =
CALCULATE (
    SUMX ( Sales, Sales[Qty] * Sales[UnitPrice] ),
    KEEPFILTERS ( Sales[Channel] = "Online" )
)

    If the expression is the same on every refresh (like Qty × UnitPrice), consider computing it upstream as a column in the source or Power Query, so the measure becomes a plain SUM.

    Watch out for measures that never return blank

    Power BI hides rows where every measure is blank. A measure that returns 0 instead of blank, for example [Sales Amount] + 0, forces the engine to evaluate and show every combination of the row and column fields, which can turn a 500-row matrix into a 500,000-row one. Only replace blanks with zeros when the business genuinely needs to see them, and only in measures used in small visuals.

    💡

    Change one thing at a time. Re-run the query in DAX Studio with a cleared cache after each change and compare the server timings. A rewrite that reads more elegantly isn't always faster, and measuring is the only way to know.

    When it isn't DAX at all

    • Too many visuals per page: each sends its own queries. Consolidate, or move detail to drillthrough pages.
    • DirectQuery sources: the time is in the source. Check the SQL generated in Performance Analyzer and tune the source, or consider aggregations or Import.
    • Bidirectional and many-to-many relationships: they expand filter propagation and can make simple queries expensive. Use them only where the model truly needs them.

    Wrapping up

    Find the slow visual with Performance Analyzer, find out where the time goes with DAX Studio, check the model's size with VertiPaq Analyzer, then change one thing and measure again. Most slow reports come down to a few causes: a bloated column, a table filter that should be a column filter, or row-by-row logic the storage engine can't handle.
