    Building a Medallion Lakehouse in Microsoft Fabric with PySpark

    The medallion architecture is easy to draw and easy to get vague about. This is a concrete version in Microsoft Fabric: what each layer holds, the PySpark that moves data between them, and how the gold layer feeds Direct Lake.

    Ronald Balza
    BI Reporting Analyst
    Nov 12, 2025•8 min read

    A Fabric lakehouse stores tables as Delta Parquet in OneLake. You can query them with Spark, with T-SQL through the SQL analytics endpoint, and from Power BI with Direct Lake. The medallion architecture is a way of organising those tables into layers of increasing quality, so it's always clear which data is raw, which is cleaned and which is ready for reporting.

    Teams split this in different ways: one lakehouse per layer, or one lakehouse with clear naming. Separate lakehouses make permissions easier (analysts can be given gold only); a single lakehouse is simpler to start with. The code below assumes a notebook with a default lakehouse attached, so relative paths like Files/… and table names resolve against it.

    Bronze: land the data as-is

    Bronze is an append-only copy of what arrived, with enough metadata to trace every row back to its source file. Don't clean anything here; if a transformation is wrong later, you can rebuild silver from bronze. 

    from pyspark.sql import functions as F

raw = (
    spark.read
         .option("header", True)
         .csv("Files/landing/orders/2025/11/*.csv")
)

bronze = (
    raw.withColumn("_source_file", F.col("_metadata.file_path"))
       .withColumn("_ingested_at", F.current_timestamp())
)

bronze.write.mode("append").format("delta").saveAsTable("bronze_orders")
    💡

    Reading everything as strings is fine in bronze. Leaving inferSchema off means a malformed value in a new file can't fail the ingestion or silently change a column type. Typing happens in silver, where you can handle bad values deliberately.

    Silver: type, clean, deduplicate and merge

    Silver holds one clean row per business key. The notebook reads new bronze rows, casts types, keeps only the latest version of each order and merges into the silver table: 

    from delta.tables import DeltaTable
from pyspark.sql import Window

# Only rows ingested since the last successful silver load
last_load = spark.sql(
    "SELECT COALESCE(MAX(_ingested_at), TIMESTAMP '1900-01-01') AS ts FROM silver_orders"
).first()["ts"]

typed = (
    spark.table("bronze_orders")
         .where(F.col("_ingested_at") > F.lit(last_load))
         .select(
             F.col("order_id").cast("bigint"),
             F.col("customer_id").cast("string"),
             F.to_date("order_date", "yyyy-MM-dd").alias("order_date"),
             F.col("status"),
             F.col("amount").cast("decimal(18,2)"),
             F.to_timestamp("updated_at").alias("updated_at"),
             "_ingested_at",
         )
         .where(F.col("order_id").isNotNull())
)

# Keep the latest version of each order within this batch
latest = (
    typed.withColumn(
             "_rn",
             F.row_number().over(
                 Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
             ),
         )
         .where("_rn = 1")
         .drop("_rn")
)

target = DeltaTable.forName(spark, "silver_orders")
(
    target.alias("t")
          .merge(latest.alias("s"), "t.order_id = s.order_id")
          .whenMatchedUpdateAll(condition="s.updated_at >= t.updated_at")
          .whenNotMatchedInsertAll()
          .execute()
)

    The condition on the update stops an older, late-arriving file from overwriting a newer version. The first time, create silver_orders with the target schema (for example by writing an empty DataFrame with saveAsTable) so DeltaTable.forName has something to merge into.

    This watermark approach is deliberately simple. For larger volumes, Delta's change data feed or Spark Structured Streaming with checkpoints give you the same "only new rows" behaviour with less custom state.

    Gold: model for reporting

    Gold is shaped for the semantic model: a star schema with clean names, conformed dimensions and facts at a clear grain. Because Direct Lake reads Delta tables (views cause DirectQuery fallback on the SQL analytics endpoint), the gold layer should be materialised as tables: 

    fact_sales = spark.sql("""
    SELECT o.order_id,
           CAST(date_format(o.order_date, 'yyyyMMdd') AS INT) AS date_key,
           c.customer_key,
           o.amount AS sales_amount
    FROM   silver_orders o
    LEFT JOIN gold_dim_customer c
           ON c.customer_id = o.customer_id
    WHERE  o.status <> 'CANCELLED'
""")

fact_sales.write.mode("overwrite").format("delta").saveAsTable("gold_fact_sales")

    A full overwrite is fine for small and medium facts and is the easiest to reason about. When it becomes too slow, switch to a merge or partition-level overwrite, just as in silver.

    Keep the tables healthy

    Frequent small writes produce many small Parquet files, which slows down Spark, the SQL endpoint and Direct Lake alike. Compact regularly: 

    OPTIMIZE gold_fact_sales VORDER;

-- Remove files no longer referenced by the table (default retention is 7 days)
VACUUM gold_fact_sales;

    V-Order is a Fabric write-time optimisation of Parquet files that makes them faster to read, especially for Direct Lake. The lakehouse UI also offers Maintenance on each table to run optimise and vacuum without writing code.

    Orchestrate with a data pipeline

    Each layer gets its own notebook, and a Fabric data pipeline runs them in order with a Notebook activity per step, connected on success. Mark a cell as a parameter cell in each notebook, and the pipeline can pass values such as a load date or a source folder: 

    # Parameters cell (toggle "parameter cell" on this cell in the notebook)
load_date = "2025-11-12"
source_folder = "Files/landing/orders"

    Add a failure path that sends an alert (an Office 365 Outlook or Teams activity) so a broken load is noticed before the morning reports are opened.

    Serving gold with Direct Lake

    From the lakehouse, create a new semantic model, select the gold tables, define relationships and add measures. The model reads the Delta tables directly; there's no import refresh to schedule. By default the model picks up changes to the Delta tables automatically, or you can switch that off and "reframe" the model as the last step of the pipeline so reports only see data once the whole load has finished.

    ⚠️

    Check the guardrails for your SKU. Direct Lake has per-capacity limits on rows per table and Parquet files per table, among others. If a gold table exceeds them on an F SKU, queries fall back to DirectQuery (or fail, depending on the model's settings), so size gold tables with those limits in mind.

    Wrapping up

    Bronze keeps what arrived, silver makes it correct, gold makes it useful. In Fabric each layer is just a set of Delta tables, which means Spark, SQL and Power BI all read the same data with no copies between them. Keep the layers disciplined, keep the tables compacted, and Direct Lake gives you import-like performance without import refreshes.
