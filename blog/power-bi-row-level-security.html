    Row-Level Security in Power BI: Static, Dynamic and Hierarchy Patterns

    Row-level security is easy to switch on and easy to get subtly wrong. These are the three patterns that cover most requirements, how to test them, and the workspace setting that quietly bypasses all of it.

    Ronald Balza
    BI Reporting Analyst
    Apr 1, 2025•7 min read

    Row-level security (RLS) restricts which rows of data a user can see in a semantic model. One report can then serve every region, cost centre or client, with each viewer seeing only their own slice. It's defined with DAX filter expressions on roles, and it applies to every report and every query against the model, including Analyze in Excel.

    How RLS works

    A role contains one or more table filters. Each filter is a DAX expression that returns TRUE or FALSE for each row of a table. Rows that return FALSE are hidden, and the filter then propagates through relationships exactly as a slicer would: filter the Region dimension and every fact table related to it is filtered too.

    That's why RLS filters belong on dimension tables. Filtering the dimension lets the model's relationships do the work, and it's far cheaper than filtering a large fact table row by row.

    Pattern 1 — Static roles

    The simplest form: one role per slice, with a hard-coded filter. In Power BI Desktop go to Modeling → Manage roles, create a role and add a filter on the Region table: 

    'Region'[Region] = "APAC"

    Static roles are fine for a handful of stable groups. They don't scale: twenty regions means twenty roles, and every reorganisation means editing and republishing the model.

    Pattern 2 — Dynamic RLS with a security table

    Dynamic RLS uses a single role whose filter depends on who is signed in. USERPRINCIPALNAME() returns the signed-in user's UPN (usually their email address) in the Power BI service. Combine it with a security table that maps users to the data they may see:

    UserEmailRegionKey
    ana@contoso.com1
    ana@contoso.com3
    ben@contoso.com2

    Ideally this table lives in the warehouse and is maintained by the business (or synced from an HR or directory source), so access changes don't require a model change. There are two common ways to wire it in.

    Option A: filter the dimension with a lookup

    Keep the security table disconnected (no relationships) and use it inside the role filter on Region: 

    -- Role "Region access", filter on table 'Region'
'Region'[RegionKey]
    IN CALCULATETABLE (
        VALUES ( 'Security'[RegionKey] ),
        'Security'[UserEmail] = USERPRINCIPALNAME ()
    )

    This is explicit and easy to read, and it supports one user mapping to many regions.

    Option B: relate the security table to the dimension

    Create a relationship from Security[RegionKey] to Region[RegionKey] (many-to-one) and filter the security table itself: 

    -- Role filter on table 'Security'
'Security'[UserEmail] = USERPRINCIPALNAME ()

    For that filter to reach Region and the facts, the relationship has to filter in both directions, with Apply security filter in both directions ticked in the relationship settings. It works, but bidirectional relationships make the model harder to reason about, so I generally prefer Option A.

    💡

    Hide the security table. Users with RLS applied can still see table and column names in the field list. Hide the security table in report view, and consider object-level security if the existence of a table or column is itself sensitive.

    Pattern 3 — Manager hierarchies with PATH

    A common requirement: "managers see their own data and everyone below them." With an Employee table that has EmployeeID, ManagerID and Email, add a calculated column holding each employee's chain of managers: 

    -- Calculated column on Employee
Manager Path = PATH ( Employee[EmployeeID], Employee[ManagerID] )

    PATH returns a pipe-delimited string from the top of the hierarchy down to the employee, e.g. 1|4|17. The role filter then keeps any employee whose path contains the signed-in user's ID: 

    -- Role filter on table 'Employee'
VAR _me =
    LOOKUPVALUE ( Employee[EmployeeID], Employee[Email], USERPRINCIPALNAME () )
RETURN
    PATHCONTAINS ( Employee[Manager Path], _me )

    Facts related to Employee (sales by rep, timesheets, tickets) are filtered to the user's whole reporting line. If a user isn't in the table, _me is blank and they see nothing, which is the safe default.

    Testing RLS properly

    • In Desktop: Modeling → View as, then tick the role and Other user to enter a specific email. This is the only way to test dynamic roles in Desktop, because by default USERPRINCIPALNAME() returns your own account.
    • In the service: on the semantic model, open Security, choose the role's … menu and select Test as role. You can test as a specific user from there too.
    • Test the edges: a user in no group, a user in several, a guest user from another tenant, and a manager at the top of a hierarchy.

    The workspace-role trap

    ⚠️

    RLS only applies to users with the Viewer role in the workspace. Admins, Members and Contributors can edit the semantic model, so they see all data regardless of roles. Share reports with restricted users through a workspace app, direct sharing or the Viewer role, and keep the editing roles for the people who build the model.

    Also remember that publishing a model doesn't assign anyone to a role. After publishing, add users or (better) security groups to each role under the semantic model's Security settings. A user who isn't in any role on an RLS-enabled model can't see any data at all.

    Wrapping up

    Put RLS filters on dimensions, drive them from a security table rather than hard-coded roles, use PATH for hierarchies, and test as specific users before go-live. And when RLS "doesn't work", check workspace roles and role membership before the DAX: those are the usual culprits.
