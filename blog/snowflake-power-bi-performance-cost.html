    Connecting Power BI to Snowflake: Storage Modes, Warehouse Sizing and Cost Control

    Power BI and Snowflake work well together, but the defaults can produce slow reports and surprising credit usage. These are the decisions that matter: storage mode, warehouse setup, the reporting layer and monitoring.

    Ronald Balza
    BI Reporting Analyst
    Sep 3, 2026•8 min read

    Every Power BI query against Snowflake runs on a virtual warehouse, and a running warehouse consumes credits. That simple fact drives most of the design decisions below. A model refreshed twice a day costs very little; a DirectQuery report opened by two hundred people every morning, each page firing a dozen queries, is a different story.

    Choose the storage mode deliberately

    ModeSnowflake loadFreshnessUse when
    ImportOnly during refreshAs of last refreshThe default. Most reporting is fine with hourly or daily data.
    DirectQueryEvery visual, every interactionLiveData must be current to the minute, or is too large to import.
    CompositeOnly for DirectQuery tablesMixedLarge detail fact in DirectQuery; dimensions and aggregates imported.

    In a composite model, set dimension tables to Dual storage mode: they're imported, but can also act as DirectQuery tables when joined to a DirectQuery fact, which avoids slow cross-source joins. Add an imported aggregation table (for example, sales by day, product and region) and configure Manage aggregations, and most visuals are answered from memory, with only drill-to-detail reaching Snowflake.

    Give Power BI its own warehouse

    Don't let Power BI share a warehouse with ETL. A dedicated warehouse makes BI costs visible, prevents a heavy transformation job from slowing reports, and lets you tune the settings for short, bursty queries: 

    CREATE WAREHOUSE IF NOT EXISTS bi_wh
  WAREHOUSE_SIZE      = 'XSMALL'
  AUTO_SUSPEND        = 60          -- seconds idle before suspending
  AUTO_RESUME         = TRUE
  INITIALLY_SUSPENDED = TRUE
  COMMENT = 'Power BI refresh and DirectQuery';

-- Cap monthly spend: notify at 80%, suspend at 100%
CREATE RESOURCE MONITOR bi_monitor
  WITH CREDIT_QUOTA = 100
       FREQUENCY = MONTHLY
       START_TIMESTAMP = IMMEDIATELY
  TRIGGERS ON 80 PERCENT DO NOTIFY
           ON 100 PERCENT DO SUSPEND;

ALTER WAREHOUSE bi_wh SET RESOURCE_MONITOR = bi_monitor;
    • Auto-suspend. Billing is per second with a 60-second minimum each time a warehouse resumes. A short auto-suspend suits refresh workloads; for DirectQuery, a slightly longer value can avoid constant suspend/resume cycles and keeps the warehouse's local cache warm.
    • Size vs concurrency. A bigger warehouse makes individual heavy queries faster. Many users running small queries at once is a concurrency problem, which multi-cluster warehouses (Enterprise edition and above) address by adding clusters with MAX_CLUSTER_COUNT.
    • A SUSPEND trigger stops queries once the quota is used. That protects the budget but also stops reports; agree on it with the business, or use NOTIFY only.

    Use a reporting role and a reporting schema

    Power BI should connect with a role that can read only the reporting layer, using only the BI warehouse: 

    CREATE ROLE IF NOT EXISTS powerbi_reader;

GRANT USAGE ON WAREHOUSE bi_wh                   TO ROLE powerbi_reader;
GRANT USAGE ON DATABASE analytics                TO ROLE powerbi_reader;
GRANT USAGE ON SCHEMA analytics.reporting        TO ROLE powerbi_reader;
GRANT SELECT ON ALL VIEWS IN SCHEMA analytics.reporting    TO ROLE powerbi_reader;
GRANT SELECT ON FUTURE VIEWS IN SCHEMA analytics.reporting TO ROLE powerbi_reader;

    The reporting schema contains star-schema views (or tables) with business-friendly column names and the right data types. Power BI then imports clean tables with no transformation in Power Query, and every report built on the warehouse uses the same definitions.

    💡

    Watch the data types. Snowflake NUMBER columns with a scale (e.g. NUMBER(38,6)) import as decimals; IDs stored as NUMBER(38,0) import as whole numbers. Cast deliberately in the view, and avoid importing high-precision timestamps where a date will do: fewer unique values compress far better in the VertiPaq engine.

    Connecting from Power BI

    The Snowflake connector takes the account URL and warehouse, and optionally a role. Setting the role explicitly avoids depending on the user's default role: 

    let
    Source    = Snowflake.Databases(
                    "myorg-myaccount.snowflakecomputing.com",
                    "BI_WH",
                    [Role = "POWERBI_READER"]
                ),
    Analytics = Source{[Name = "ANALYTICS", Kind = "Database"]}[Data],
    Reporting = Analytics{[Name = "REPORTING", Kind = "Schema"]}[Data],
    FactSales = Reporting{[Name = "FACT_SALES", Kind = "View"]}[Data]
in
    FactSales

    For scheduled refresh in the service, the semantic model needs credentials for a dedicated service user rather than a person's account (Snowflake is phasing out password-only sign-in, so check which authentication methods your connector and gateway versions support) and, if Snowflake is reachable only over a private network, a gateway. For DirectQuery, Microsoft Entra ID single sign-on passes each report viewer's identity to Snowflake, so Snowflake's own row access policies and roles apply per user. It requires a Snowflake security integration for Entra ID and enabling the setting in the Power BI admin portal.

    Monitor what Power BI actually costs

    Credit usage per warehouse is in ACCOUNT_USAGE. Run this weekly, or put it in its own small report: 

    -- Credits used by the BI warehouse per day
SELECT DATE_TRUNC('day', start_time) AS usage_day,
       SUM(credits_used)             AS credits
FROM   snowflake.account_usage.warehouse_metering_history
WHERE  warehouse_name = 'BI_WH'
  AND  start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP  BY 1
ORDER  BY 1;

-- Slowest Power BI queries in the last week
SELECT query_text,
       total_elapsed_time / 1000 AS seconds,
       bytes_scanned,
       user_name
FROM   snowflake.account_usage.query_history
WHERE  warehouse_name = 'BI_WH'
  AND  start_time >= DATEADD('day', -7, CURRENT_TIMESTAMP())
ORDER  BY total_elapsed_time DESC
LIMIT  20;

    (ACCOUNT_USAGE views have some latency, typically up to a few hours, so they're for trends rather than live monitoring.) The slow-query list usually points straight at the fix: a missing filter, a view doing heavy work at query time that should be materialised, or a large table that would benefit from a clustering key on the column reports filter by most.

    Let the caches help

    Snowflake's result cache returns the result of an identical query for 24 hours without using the warehouse at all, as long as the underlying data hasn't changed. Import refreshes rarely benefit, but DirectQuery reports often do: many users opening the same landing page generate identical queries. Avoid non-deterministic functions such as CURRENT_TIMESTAMP() in reporting views, because they prevent result reuse.

    Wrapping up

    Default to Import, use composite models with aggregations when you need DirectQuery, give Power BI its own small warehouse with a resource monitor, and connect through a read-only role to a curated reporting schema. Then check warehouse metering regularly. Snowflake makes the cost of every query visible, which makes it straightforward to keep under control.
