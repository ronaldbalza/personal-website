    From Raw Data to Dashboard: An End-to-End Power BI Build

    A walkthrough of the order I build a Power BI solution in, from the first conversation about requirements to a scheduled refresh in the Service, with the Power Query and DAX that hold it together.

    Ronald Balza
    BI Reporting Analyst
    Nov 7, 2023•8 min read

    Most Power BI tutorials start with "Get data" and end with a chart. Real projects start earlier, with what the report is for, and end later, with refresh, security and handover. This walkthrough follows the full sequence using a typical small-to-mid-size setup: sales transactions in a SQL database, budgets maintained in Excel files on SharePoint, and a report for a sales leadership team.

    Step 1 — Pin down requirements and grain

    Before connecting to anything, agree three things with the people who'll use the report:

    1. The questions. "How are sales tracking against budget by region and month?" is buildable. "Show me sales" is not.
    2. The KPI definitions. Does revenue include tax? Are returns netted off? Which date counts: order, invoice or ship date?
    3. The grain of each fact. Sales are at transaction-line level; budgets are usually at month × region × product category. Different grains are fine, but they shape the model.

    Writing these down saves the most expensive kind of rework: rebuilding a model because a definition changed after the report went live.

    Step 2 — Connect and stage in Power Query

    I organise Power Query into staging queries (one per source table, minimal changes, load disabled) and model queries that reference them and shape the final tables. Right-click a staging query and untick Enable load so it doesn't become a table in the model.

    For the SQL source, select only the columns you need and filter early so the work folds back to the database:

    // stg_SalesLines  (Enable load: off)
let
    Source   = Sql.Database("sql-prod-01", "SalesDB"),
    Lines    = Source{[Schema = "dbo", Item = "SalesOrderLines"]}[Data],
    Columns  = Table.SelectColumns(Lines,
                 {"OrderID", "LineNo", "OrderDate", "CustomerID", "ProductID", "Qty", "NetAmount"}),
    Recent   = Table.SelectRows(Columns, each [OrderDate] >= #date(2020, 1, 1))
in
    Recent

    For the budget workbooks, the SharePoint folder connector combines every file in a library folder:

    // stg_Budget  (Enable load: off)
let
    Source   = SharePoint.Files("https://contoso.sharepoint.com/sites/Finance", [ApiVersion = 15]),
    Budgets  = Table.SelectRows(Source, each
                 Text.Contains([Folder Path], "/Budgets/") and [Extension] = ".xlsx"),
    Sheets   = Table.AddColumn(Budgets, "Data", each
                 Excel.Workbook([Content], true){[Item = "Budget", Kind = "Sheet"]}[Data]),
    Combined = Table.Combine(Sheets[Data]),
    Typed    = Table.TransformColumnTypes(Combined, {
                 {"Month", type date}, {"Region", type text},
                 {"Category", type text}, {"Budget", Currency.Type}})
in
    Typed
    💡

    Use SharePoint.Files with the site URL, not a synced OneDrive path. A local path only works on your machine; the site URL works in the Service, and SharePoint Online sources don't need an on-premises gateway.

    Step 3 — Shape a star schema

    The model should have fact tables holding numbers at a defined grain, surrounded by dimension tables holding the attributes you filter and group by. For this report:

    • Sales (fact, one row per order line) and Budget (fact, one row per month × region × category)
    • Customer, Product, Region and Date (dimensions)

    Relationships go from dimension (one) to fact (many), single direction. Because Budget is at category level, it relates to a Category column, so either add a small Product Category dimension shared by both facts, or relate budget to a category-level table and let product filter sales only. A shared dimension is cleaner: one slicer filters both facts.

    Add a dedicated date table and mark it as a date table, since every time intelligence calculation depends on it. It can be built in DAX or in Power Query; the Power Query version looks like this: 

    // Date
let
    StartDate = #date(2020, 1, 1),
    EndDate   = #date(Date.Year(DateTime.LocalNow()), 12, 31),
    Dates     = List.Dates(StartDate, Duration.Days(EndDate - StartDate) + 1, #duration(1, 0, 0, 0)),
    Base      = Table.FromList(Dates, Splitter.SplitByNothing(), {"Date"}),
    Typed     = Table.TransformColumnTypes(Base, {{"Date", type date}}),
    Year      = Table.AddColumn(Typed, "Year", each Date.Year([Date]), Int64.Type),
    MonthNo   = Table.AddColumn(Year, "Month Number", each Date.Month([Date]), Int64.Type),
    Month     = Table.AddColumn(MonthNo, "Month", each Date.ToText([Date], "MMM"), type text),
    MonthStart= Table.AddColumn(Month, "Month Start", each Date.StartOfMonth([Date]), type date)
in
    MonthStart

    Set Month to sort by Month Number in the model, and relate Budget[Month] (first of the month) to Date[Date].

    Step 4 — Write base measures, then derived ones

    Keep measures in a dedicated, empty "measure table" so they're easy to find, and hide the raw numeric columns so report authors use measures rather than implicit sums. 

    Sales Amount = SUM ( Sales[NetAmount] )

Budget Amount = SUM ( Budget[Budget] )

Variance to Budget = [Sales Amount] - [Budget Amount]

Variance to Budget % = DIVIDE ( [Variance to Budget], [Budget Amount] )

    Every report-level number should be built from these. When the definition of "sales" changes, you change one measure.

    Step 5 — Build the report

    Build pages in the order the requirements listed the questions: a summary page with KPI cards for sales, budget and variance; a trend page; and a detail page reached by drillthrough on region or customer. Check every total against a known figure from the source system before anyone else sees the report; reconciling early is what builds trust in a new dashboard.

    Step 6 — Publish, refresh and share

    1. Publish to a workspace dedicated to the project, not My workspace.
    2. Gateway. An on-premises SQL Server needs an on-premises data gateway, with the server and database added as a data source connection. SharePoint Online doesn't.
    3. Scheduled refresh. Set credentials on the semantic model and schedule refresh to run after the source systems have finished their overnight loads. Pro allows up to 8 scheduled refreshes a day; Premium capacity allows up to 48.
    4. Share through an app. Package the report in a workspace app so users get a stable entry point and you can keep developing in the workspace without disrupting them.
    ⚠️

    Plan for growth. If the sales table will grow into tens of millions of rows, configure incremental refresh (RangeStart/RangeEnd parameters filtering OrderDate) before the first big publish, so each refresh only reloads recent partitions.

    Wrapping up

    The build order matters more than any individual technique: definitions before data, staging before shaping, a star schema before measures and measures before visuals. Follow it and the final report is quick to build, easy to change and much easier to hand over.
