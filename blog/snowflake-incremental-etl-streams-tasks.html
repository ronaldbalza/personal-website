    Designing Incremental ETL Pipelines in Snowflake with Streams, Tasks and MERGE

    Full reloads are easy to write and expensive to run. Streams, tasks and a well-shaped MERGE let Snowflake process only the rows that changed, and keep reporting tables fast and trustworthy.

    Ronald Balza
    BI Reporting Analyst
    Jun 9, 2026•10 min read

    The first version of most warehouse pipelines is a CREATE OR REPLACE TABLE … AS SELECT that rebuilds everything on every run. It's simple and correct, and it becomes a problem as soon as the source tables grow: every refresh re-reads history that hasn't changed, burns warehouse credits and pushes back the time reports are ready.

    Snowflake has native building blocks for doing this incrementally. This article walks through the pattern I reach for: a stream to capture changes, a MERGE to apply them, and a task to run it on a schedule. It ends with Dynamic Tables, which cover a lot of the same ground with far less code.

    How a stream tracks changes

    A stream doesn't copy data. It stores an offset, a point in the source table's version history, and when you query it, Snowflake returns the rows that changed between that offset and now. Each row comes with three metadata columns:

    ColumnMeaning
    METADATA$ACTIONINSERT or DELETE
    METADATA$ISUPDATETRUE when the row is one half of an update. An update appears as a DELETE of the old values plus an INSERT of the new ones.
    METADATA$ROW_IDA stable identifier for the row, used to follow it across changes

    The key behaviour: the offset only moves when the stream is consumed by a DML statement in a transaction that commits. A plain SELECT from the stream doesn't advance it, so you can inspect what's pending without losing anything. If the MERGE fails, the transaction rolls back and the same changes are still there on the next run. 

    -- Standard stream: captures inserts, updates and deletes
CREATE OR REPLACE STREAM raw.orders_stream ON TABLE raw.orders;

-- If the source is insert-only (e.g. an event log), an append-only
-- stream is cheaper because it never has to compute deletes
CREATE OR REPLACE STREAM raw.events_stream
  ON TABLE raw.events
  APPEND_ONLY = TRUE;

-- See what is pending without consuming it
SELECT METADATA$ACTION, METADATA$ISUPDATE, order_id, status, updated_at
FROM   raw.orders_stream;

    Applying changes with MERGE

    The MERGE needs to handle three cases: new rows, changed rows and deleted rows. Because an update arrives as a DELETE/INSERT pair, the trick is to treat the INSERT side as the new version of the row and only act on a DELETE when it isn't part of an update. 

    MERGE INTO curated.orders AS tgt
USING (
    SELECT *
    FROM   raw.orders_stream
    -- keep inserts (new rows and the "after" side of updates)
    -- and true deletes; drop the "before" side of updates
    WHERE  NOT (METADATA$ACTION = 'DELETE' AND METADATA$ISUPDATE)
    -- if the same key changed more than once since the last run,
    -- keep only its latest version
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY order_id
        ORDER BY updated_at DESC
    ) = 1
) AS src
    ON tgt.order_id = src.order_id
WHEN MATCHED AND src.METADATA$ACTION = 'DELETE' THEN
    DELETE
WHEN MATCHED AND src.METADATA$ACTION = 'INSERT' THEN
    UPDATE SET
        tgt.customer_id = src.customer_id,
        tgt.status      = src.status,
        tgt.amount      = src.amount,
        tgt.updated_at  = src.updated_at,
        tgt._loaded_at  = CURRENT_TIMESTAMP()
WHEN NOT MATCHED AND src.METADATA$ACTION = 'INSERT' THEN
    INSERT (order_id, customer_id, status, amount, updated_at, _loaded_at)
    VALUES (src.order_id, src.customer_id, src.status, src.amount,
            src.updated_at, CURRENT_TIMESTAMP());
    ⚠️

    Deduplicate the source. If two source rows match the same target row, Snowflake raises a "duplicate row detected during DML action" error by default (controlled by the ERROR_ON_NONDETERMINISTIC_MERGE parameter). The QUALIFY ROW_NUMBER() filter above guarantees one source row per key. Don't switch the parameter off to make the error go away; that just makes the result depend on which row Snowflake happens to process last.

    This shape is also idempotent: running it twice against the same changes gives the same result, which is what lets you retry safely.

    Scheduling it with a task

    A task runs a single SQL statement (or a stored procedure call) on a schedule. Adding a WHEN SYSTEM$STREAM_HAS_DATA(…) condition means the task skips runs when nothing has changed. That check runs in the cloud services layer without resuming the warehouse, so an idle schedule doesn't burn warehouse credits. 

    CREATE OR REPLACE TASK etl.merge_orders
  WAREHOUSE = transform_wh
  SCHEDULE  = '15 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('raw.orders_stream')
AS
  MERGE INTO curated.orders AS tgt
  USING ( … same source query as above … ) AS src
  ON tgt.order_id = src.order_id
  …;

-- Tasks are created suspended
ALTER TASK etl.merge_orders RESUME;

    A few practical points:

    • Cron schedules work too: SCHEDULE = 'USING CRON 0 6 * * * Australia/Sydney' runs daily at 6 am in that time zone.
    • Serverless tasks. Omit WAREHOUSE and Snowflake manages the compute for you. You can set a starting size with USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE. This suits short, frequent jobs that would otherwise keep waking a warehouse.
    • Task graphs. Downstream steps use AFTER etl.merge_orders instead of their own schedule, so a fact table only loads after its dimensions. Only the root task has a schedule; you resume the children before the root.
    • Privileges. The role that owns the task needs EXECUTE TASK on the account, plus usage on the warehouse and the objects it touches.

    Monitoring, and the stale-stream trap

    Task runs are recorded in task history, which is the first place to look when data looks late:

    SELECT name, state, scheduled_time, completed_time, error_message
FROM   TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
           TASK_NAME => 'MERGE_ORDERS',
           SCHEDULED_TIME_RANGE_START => DATEADD('day', -2, CURRENT_TIMESTAMP())))
ORDER  BY scheduled_time DESC;

    The failure that catches people out is a stale stream. A stream depends on the source table's Time Travel history. If it isn't consumed within the table's data retention period (Snowflake will extend retention up to MAX_DATA_EXTENSION_TIME_IN_DAYS, 14 days by default, to protect unconsumed streams), the offset falls outside available history and the stream becomes stale. At that point it has to be recreated and the target reloaded in full. This usually happens when a task was suspended for a release and nobody resumed it. SHOW STREAMS returns a stale_after column; it's worth alerting on.

    When Dynamic Tables are the better answer

    Streams and tasks give you full control, but for many transformations you're writing plumbing that Snowflake can manage for you. A Dynamic Table is defined by a query and a target freshness, and Snowflake works out how to keep it up to date, incrementally where the query allows it: 

    CREATE OR REPLACE DYNAMIC TABLE curated.daily_sales
  TARGET_LAG = '30 minutes'
  WAREHOUSE  = transform_wh
AS
SELECT order_date,
       customer_id,
       SUM(amount) AS sales_amount,
       COUNT(*)    AS order_count
FROM   curated.orders
GROUP  BY order_date, customer_id;

    Check the refresh_mode column in SHOW DYNAMIC TABLES: if Snowflake can't refresh your query incrementally, it falls back to a full refresh, which may cost more than the stream-based version.

    UseWhen
    Streams + tasks + MERGEYou need explicit control over deletes, soft-delete flags, audit columns, SCD logic or calls to stored procedures.
    Dynamic TablesThe transformation is a declarative SELECT (joins, aggregates, filters) and "fresh within N minutes" is a good enough contract.
    High-watermark queryThe source lives outside Snowflake and you're pulling with an external tool. Filter on a reliable updated_at and store the last value loaded.

    Wrapping up

    Incremental loading in Snowflake comes down to three questions: how do I know what changed (stream or watermark), how do I apply it safely (a deduplicated, idempotent MERGE), and what runs it (a task, or Snowflake itself via a Dynamic Table). Get those right and the pipeline costs scale with the volume of change instead of the size of history, and the reporting layer on top stays fresh without anyone rebuilding tables by hand.
