    Reporting on Salesforce and Dynamics 365 Data in One Pipeline Model

    When sales teams run on two CRMs, leadership still wants one pipeline number. Here's how to map Salesforce and Dynamics 365 opportunities into a single model without losing what each system means by "won".

    Ronald Balza
    BI Reporting Analyst
    Apr 28, 2026•8 min read

    Two CRMs in one business is more common than it sounds: acquisitions, regional teams that picked different tools, or a marketing org on one platform and sales on another. Each system has its own data model, its own way of representing stages and its own idea of what an "amount" is. Pointing Power BI at both and appending the tables gives you a number, but not one anyone should trust.

    The approach that holds up is to define a common opportunity model in the warehouse, map each CRM into it explicitly, and keep the mappings in tables the business can review.

    Map the fields first

    Start with the fields the pipeline report actually needs. These are the standard fields in each system (custom fields will vary by org):

    Common fieldSalesforce OpportunityDynamics 365 opportunity
    Source IDIdopportunityid
    NameNamename
    AccountAccountIdparentaccountid
    OwnerOwnerIdownerid
    StageStageNamesalesstage / stepname
    Open / won / lostIsClosed, IsWonstatecode (0 Open, 1 Won, 2 Lost)
    AmountAmountestimatedvalue (open), actualvalue (won)
    Close dateCloseDateestimatedclosedate, actualclosedate
    ProbabilityProbabilitycloseprobability
    CurrencyCurrencyIsoCode (multi-currency orgs)transactioncurrencyid, plus *_base columns
    Last modifiedSystemModstamp / LastModifiedDatemodifiedon

    Note the asymmetry: Salesforce has one Amount and one CloseDate, while Dynamics separates estimated and actual values. Decide the rule once (for example, "use actual value and actual close date when won, estimated otherwise") and implement it in the conform layer, not in DAX.

    Align stages and status with a mapping table

    Stage names are configured per org, and both systems allow custom stages. Hard-coding them in a CASE statement means a code change every time sales ops renames a stage. Put them in a mapping table instead: 

    CREATE TABLE conform.map_opportunity_stage (
    source_system   VARCHAR(20),   -- 'SALESFORCE' | 'DYNAMICS'
    source_stage    VARCHAR(100),  -- value as it appears in the CRM
    common_stage    VARCHAR(50),   -- 'Qualify', 'Develop', 'Propose', 'Negotiate', 'Closed'
    stage_order     INT,
    is_pipeline     BOOLEAN        -- counts toward open pipeline?
);

    For open/won/lost, rely on each system's status fields rather than stage names: IsClosed/IsWon in Salesforce (derived from the stage's configured type) and statecode in Dynamics. They're stable even when stage labels change.

    Build the conformed view

    Each source gets its own SELECT that produces exactly the same columns, then the results are unioned. A source-prefixed key keeps IDs from colliding: 

    CREATE OR REPLACE VIEW conform.opportunity AS
SELECT
    'SF-' || o.id                                   AS opportunity_key,
    'SALESFORCE'                                    AS source_system,
    o.name                                          AS opportunity_name,
    am.common_account_key                           AS account_key,
    o.ownerid                                       AS owner_source_id,
    sm.common_stage,
    CASE WHEN o.isclosed AND o.iswon THEN 'Won'
         WHEN o.isclosed            THEN 'Lost'
         ELSE 'Open' END                            AS status,
    o.amount                                        AS amount_txn,
    o.currencyisocode                               AS currency_code,
    o.closedate                                     AS close_date,
    o.probability / 100.0                           AS probability
FROM raw_salesforce.opportunity o
LEFT JOIN conform.map_opportunity_stage sm
       ON sm.source_system = 'SALESFORCE' AND sm.source_stage = o.stagename
LEFT JOIN conform.map_account am
       ON am.source_system = 'SALESFORCE' AND am.source_account_id = o.accountid
WHERE NOT o.isdeleted

UNION ALL

SELECT
    'D365-' || o.opportunityid,
    'DYNAMICS',
    o.name,
    am.common_account_key,
    o.ownerid,
    sm.common_stage,
    CASE o.statecode WHEN 0 THEN 'Open' WHEN 1 THEN 'Won' WHEN 2 THEN 'Lost' END,
    CASE WHEN o.statecode = 1 THEN o.actualvalue ELSE o.estimatedvalue END,
    c.isocurrencycode,
    CASE WHEN o.statecode IN (1, 2) THEN o.actualclosedate ELSE o.estimatedclosedate END,
    o.closeprobability / 100.0
FROM raw_dynamics.opportunity o
LEFT JOIN raw_dynamics.transactioncurrency c
       ON c.transactioncurrencyid = o.transactioncurrencyid
LEFT JOIN conform.map_opportunity_stage sm
       ON sm.source_system = 'DYNAMICS' AND sm.source_stage = o.stepname
LEFT JOIN conform.map_account am
       ON am.source_system = 'DYNAMICS' AND am.source_account_id = o.parentaccountid;
    💡

    Test the mappings, not just the SQL. A simple check, "rows where common_stage or account_key is null", catches every new stage or unmapped account the moment it appears, instead of weeks later when a total looks low.

    Handle currency once

    Both platforms support multiple currencies, and both convert to a corporate currency using rates maintained in the CRM: Salesforce with its currency table (and optional dated exchange rates for opportunities), Dynamics with the exchangerate on each record and the *_base columns. The catch is that two CRMs can hold different rates for the same day.

    For a combined report, I'd store the transaction amount and currency from each source and convert both with one rate table owned by finance, joined on currency and close date. Then a won deal is worth the same in reporting regardless of which CRM it came from.

    Match accounts and owners

    The same customer often exists in both CRMs with slightly different names. Automatic fuzzy matching is a useful starting point, but the result should land in a reviewed mapping table (conform.map_account above) rather than being recomputed on every run. Owners are easier: both systems store the user's email, which usually matches the corporate directory and gives you a clean shared dim_sales_rep.

    Extract incrementally

    Both systems expose a reliable modified timestamp, which makes high-watermark extraction simple.

    SELECT Id, Name, AccountId, OwnerId, StageName, IsClosed, IsWon,
       Amount, CurrencyIsoCode, CloseDate, Probability, IsDeleted, SystemModstamp
FROM   Opportunity
WHERE  SystemModstamp > 2026-04-01T00:00:00Z

    Two things to plan for:

    • Deletes. Deleted Salesforce records only appear when you query with queryAll (records in the Recycle Bin, with IsDeleted = true), and they're purged after the retention window. In Dynamics, deleted records simply disappear from the table, so you need change tracking (which Azure Synapse Link and Link to Fabric use) or a periodic full key comparison.
    • API limits. Salesforce enforces daily API request limits per org. For large objects, the Bulk API is far more efficient than paging through the REST query endpoint.

    Wrapping up

    The SQL in a multi-CRM model isn't hard. What makes it work is being explicit: a documented field map, stage and account mapping tables the business can review, one currency rule and status logic based on each system's own won/lost flags. With that in place, "pipeline" means the same thing on every page of the report, whichever CRM the deal lives in.
