    Version Control for Power BI: PBIP, TMDL, Git Integration and Deployment Pipelines

    A .pbix file is a binary blob: you can't diff it, review it or merge it. Power BI Projects change that. Here's the workflow that brings Power BI development closer to how software teams already work.

    Ronald Balza
    BI Reporting Analyst
    Mar 17, 2026•7 min read

    For years the Power BI "version control" strategy in many teams was a SharePoint folder of files named Sales_v7_FINAL_fixed.pbix. It's hard to tell what changed between versions, two people can't work on the same model, and there's no review step before a change reaches production.

    Three features fix this when used together: Power BI Project (PBIP) files that store a report and model as readable text, Git integration for Fabric workspaces, and deployment pipelines to promote content between environments.

    Power BI Projects: a model you can diff

    In Power BI Desktop, File → Save as and choose Power BI project (*.pbip). Instead of one binary file you get a folder structure: 

    Sales.pbip
Sales.SemanticModel/
    definition/
        model.tmdl
        relationships.tmdl
        tables/
            Sales.tmdl
            Date.tmdl
            Customer.tmdl
    definition.pbism
Sales.Report/
    definition/ …          (report pages and visuals as JSON)
    definition.pbir
.gitignore

    The semantic model is stored in TMDL (Tabular Model Definition Language), a readable, indentation-based format with one file per table. A measure change shows up in a pull request as a small, reviewable diff: 

    table Sales

	measure 'Sales Amount' = SUM ( Sales[NetAmount] )
		formatString: #,##0

	measure 'Sales YoY %' =
			VAR _py = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
			RETURN DIVIDE ( [Sales Amount] - _py, _py )
		formatString: 0.0%

	column NetAmount
		dataType: decimal
		summarizeBy: none
		sourceColumn: NetAmount

    Report definitions can also be saved in the PBIR format, which stores each page and visual as its own JSON file instead of one large report.json. That makes report changes reviewable too, and reduces merge conflicts when two people edit different pages.

    💡

    Don't commit data or local settings. The .pbi folders hold a local data cache (cache.abf) and user settings (localSettings.json). Desktop creates a .gitignore that excludes them; make sure it's committed so nobody pushes a cached copy of production data to the repository.

    Connecting a workspace to Git

    Fabric workspaces can be connected to a branch in Azure DevOps or GitHub (Workspace settings → Git integration). Once connected:

    • Items in the workspace (semantic models, reports, notebooks, pipelines and more) are serialised to the chosen folder in the branch.
    • The workspace shows which items have uncommitted changes, and you can commit from the service or update the workspace from the branch.
    • Developers can work locally in Desktop on a feature branch, open a pull request, and once it's merged, update the development workspace from main.

    A common pattern is one workspace per developer (each connected to their own feature branch) plus a shared development workspace connected to main. That keeps experiments out of the shared environment.

    Promoting with deployment pipelines

    Deployment pipelines link workspaces into stages, typically Development, Test and Production, and copy content forward with a comparison view that shows what's new, changed or only in one stage. Two features make them practical:

    • Deployment rules. Per stage, a semantic model can have data source rules or parameter rules, so the Test copy points at the test database and Production at production, with no manual edits after deployment. Using Power Query parameters for server and database names makes this straightforward.
    • Selective deployment. You can deploy only specific items, for example a report fix without its model, when the model change isn't ready. 
    // Parameters: ServerName, DatabaseName (Text, required)
let
    Source = Sql.Database(ServerName, DatabaseName),
    Sales  = Source{[Schema = "rpt", Item = "FactSales"]}[Data]
in
    Sales
    ⚠️

    Deploying doesn't refresh. Content deployed to a new stage needs its credentials configured and a refresh run (or scheduled) before reports show data, and a deployed schema change may require a full refresh. Include that in the release checklist.

    Automating the last mile

    Everything above can be driven from CI/CD. The Fabric and Power BI REST APIs expose Git operations (commit, update from Git) and deployment pipeline operations (deploy stage content), so a merge to main can trigger an Azure DevOps or GitHub Actions workflow that updates the dev workspace and deploys to Test. Running Tabular Editor's Best Practice Analyzer rules against the TMDL files in the same workflow catches common modelling issues (missing format strings, unhidden key columns, bidirectional relationships) before review.

    Wrapping up

    PBIP and TMDL turn Power BI content into text that can be diffed, reviewed and merged; Git integration keeps workspaces in sync with a branch; deployment pipelines move tested content to production with the right connections. It's a bit more process than saving a PBIX to SharePoint, and it's the difference between a report and a maintainable product.
